# Validating the OPEN_DRONE_ID_SELF_ID and OPEN_DRONE_ID_OPERATOR_ID streams

*Evidence for the preceding commit. DroneBlocks, 2026-08-30 and 2026-09-01.*

> ⚠️ **This file is evidence, not product.** Drop this commit before opening an
> upstream pull request; the content belongs in the PR description instead.

## The problem the streams fix

PX4 accepts `OPEN_DRONE_ID_SELF_ID` and `OPEN_DRONE_ID_OPERATOR_ID` from a ground
station and publishes both to uORB (`mavlink_receiver.cpp:3064` and `:3081`).

The **only** subscriber to those two topics in the tree is
`src/drivers/uavcan/remoteid.cpp`, which rebroadcasts them over DroneCAN. There
is no MAVLink stream for either, so a Remote ID module on a serial port never
receives them.

Forwarding does not cover the gap. QGroundControl addresses these messages to the
autopilot, per its own comment at `RemoteIDManager.cc:49`, and
`Mavlink::forward_message()` returns early when the target is the receiving
instance itself. PX4 keeps them and forwards nothing.

ArduPilot does not have this problem: `AP_OpenDroneID.cpp` stores what the GCS
sends and round-robins it back out, `send_self_id_message()` at `:526` and
`send_operator_id_message()` at `:553`. That is why a serial module such as
BlueMark's db202mav works there and not here.

## Method

A ground station was simulated with `pymavlink`, sending both messages at 1 Hz
addressed to the autopilot exactly as QGroundControl does, while counting what
the autopilot sent back. Anything Open Drone ID arriving from system 1 was
generated by PX4, since the simulated GCS transmits as system 255.

Tooling is in the `dexi-remote-id` repository, `tools/odid_probe.py`.

⚠️ QGroundControl itself cannot be used for the baseline. It does not transmit
Remote ID messages until it has received an `OPEN_DRONE_ID_ARM_STATUS` from a
device, so on a bare bench board it stays silent, and that silence would look
like the result under test.

## Result: Pixhawk 6C, `px4_fmu-v6c_default`, USB link

30 messages of each type sent over 30 s.

| Message | Stock PX4 | With these streams |
|---|---|---|
| `OPEN_DRONE_ID_LOCATION` | 1.00 Hz | 1.00 Hz |
| `OPEN_DRONE_ID_SYSTEM` | absent | absent |
| **`OPEN_DRONE_ID_SELF_ID`** | **absent** | **1.00 Hz** |
| **`OPEN_DRONE_ID_OPERATOR_ID`** | **absent** | **1.00 Hz** |

`SYSTEM` is correctly absent indoors: it requires a GPS fix and a home position.
`LOCATION` streaming unchanged at 1 Hz is the control, and confirms the Open
Drone ID stream group was active in both runs.

Total autopilot traffic was 9018 messages before and 9026 after, so nothing else
was displaced.

Reproduced on a second Pixhawk 6C, both messages returning at 1.04 Hz.

## End to end

With a Remote ID module on TELEM1 at 57600 baud, an operator ID entered at the
ground station reached the air as a valid ASTM F3411 message:

```
service data, UUID 0xFFFA
  0d af 52 00 4641334445584950524f424500...
  |  |  |  |  '- "FA3DEXIPROBE", the operator ID the GCS sent
  |  |  |  '---- Operator ID, CAA registration
  |  |  '------- message type 5, protocol version 2
  |  '---------- message counter
  '------------- ASTM Open Drone ID application code
```

Read back by an independent receiver. The module reported `missing = SYS OP_LOC`
and nothing else, so `LOC`, `SELF_ID`, `OP_ID` and `ID` had all been satisfied.

Outdoors with a GPS fix, `SYSTEM` and the operator location appear as well,
completing the set.

## A separate defect, not addressed here

PX4's arming check does not read `OPEN_DRONE_ID_ARM_STATUS`. `Commander.cpp:2826`
takes `open_drone_id_system_present` and `_healthy` from the module's
**HEARTBEAT**, and `mavlink_receiver.cpp:2193` marks it healthy only when
`system_status` is `MAV_STATE_STANDBY` or `MAV_STATE_ACTIVE`.

ArduRemoteID sends `system_status` 0, `MAV_STATE_UNINIT` (`mavlink.cpp:85`), so a
module running it can never satisfy `COM_ARM_ODID=2`. Confirmed both ways on a
6C: status 3 gives "Remote ID system regained", status 0 gives "Preflight Fail:
Open Drone ID system not ready".

That is a firmware issue on the module side and is out of scope for this change.
